# Changelog

> **Rename:** The package has been renamed to VitalWatch — package `vitalwatch`
> (`import vitalwatch`, `VitalWatchFlask`), diagnostic command `vitalwatch-status`,
> environment variables `VITALWATCH_*`, signature headers `X-VitalWatch-Signature` /
> `X-VitalWatch-Timestamp`. The history below uses the new names.


## 0.4.1

### Fixed

- Agent: ModSecurity blocks (`ModSecurity: Access denied` / `Warning` in Apache and Plesk
  `error_log`) were reported as `web_server` errors. They show the firewall working (bots
  probing `/.env`, `/.git/`), not a fault; on a Plesk server they were most of the events.
  They are now filtered as noise.
- Agent: nginx 404 scans logged as `openat() … failed (2: No such file or directory)` (newer
  nginx) were not recognised as noise like `open() …`; both forms are filtered now.

## 0.4.0

### Added

- **Dependency advisories.** The application SDK (not `vitalwatch-agent`) sends the
  installed package list of the running interpreter (`importlib.metadata`) to the hub's
  new `POST /api/i/{key}/deps` endpoint, signed like `/server` and carrying the same
  identity fields (`env`, `source`, `release`, `runtime`, `runtime_version`,
  `sdk_version`) plus a `dependencies` object (`v: 1`, `ecosystem: "PyPI"`,
  `manifest: "installed-distributions"`, `hash`, `packages`). The hub matches it against
  OSV.dev. Names are PEP 503 normalized and deduplicated; `pip`, `setuptools`, `wheel`,
  `vitalwatch` and the Debian placeholder `pkg-resources` are left out; at most 5000
  packages; a body over 500 KB is not sent (one stderr warning).
- Sent from the heartbeat thread about 60 seconds after start, then every 24 hours and
  whenever the list's hash changes (re-checked hourly). With gunicorn `--preload` only
  the master process sends.
- `VITALWATCH_DEPENDENCIES=false` turns it off.
- `vitalwatch-status` shows a `Dependencies` line (`installed distributions · N packages`
  or `disabled`); `vitalwatch-status --deps` sends the list immediately and prints the
  HTTP status. `--test` and `--vitalwatch` do not send it.

## 0.3.0

### Added

- Agent: **server status snapshot.** Every 5 minutes (and once right after start) the
  agent sends a single latest snapshot to the hub's server endpoint as a top-level
  `server_status` field in an otherwise empty body (`{"events": [], "server_status": …}`):
  short hostname, uptime, load average, CPU count, memory and swap, disk usage per real
  filesystem, failed systemd units, Docker containers (state, health, restart count, start
  time) and pending apt updates (counted at most once an hour) with the reboot-required
  flag. The hub uses it for the daily digest and the `/server` command. It is a snapshot,
  not a time series; no IP addresses are included. Each field becomes `null` if it cannot
  be collected; bodies over 7000 bytes are trimmed and marked `truncated`. A successful
  snapshot also counts as the heartbeat.
- Agent: `vitalwatch-agent status` collects one snapshot and prints it as JSON without
  sending it. `vitalwatch-agent check` shows a `Status snapshot` line with the update
  counting method (`apt-check`, `apt-get` or `not available`).

## 0.2.4

### Fixed

- Agent: PHP-FPM on Plesk (Ubuntu/Debian) was reported as `not found`. Plesk writes the
  master log to `/var/log/plesk-phpXY-fpm/error.log`, which is now watched as part of the
  `php_fpm` source.

## 0.2.3

### Changed

- Docs: README, CHANGELOG and package description are now in English.
- All user-visible output (CLI, log warnings, IDE docs) is now in English:
  `vitalwatch-status` and `vitalwatch-agent check` labels and messages (`SDK version`,
  `Latest version`, `could not check`, `Update available: …`, `Release tag … (source: …)`,
  `Configuration OK.`), agent source statuses (`found` / `not found` / `not readable` /
  `disabled`), agent stderr warnings, `agent.ini` validation errors, argparse help, the
  generated systemd unit, and the docstrings of the public API (`vitalwatch.init`,
  `report`, `hook_process`, `VitalWatchFlask`, the Django and ASGI middleware, `Reporter`,
  `scrubber`). Scripts that grep the old Turkish output must be updated; exit codes are
  unchanged. The client error reason `govde-kodlanamadi` is now `body-encode-failed`.
- **Fingerprint side effect:** the test events sent by `vitalwatch-status --test` and
  `vitalwatch-agent check --test` now read `Test event generated by …`; they are grouped
  once under a new fingerprint in the dashboard. Other generated event messages
  (HTTP 5xx, slow request, agent events) were already English and are unchanged.

## 0.2.2

### Changed

- **Plain CamelCase names are no longer turned into `[token]`.** The long-string mask
  (24+ characters) also mistook class and method names such as
  `InvalidOperationException` and `HandleNonSuccessAndDebuggerNotification` for tokens,
  making stack traces unreadable. A candidate that contains no digits or `-`/`_` and fully
  matches `^[A-Za-z][a-z]+(?:[A-Z][a-z]+)+$` is no longer treated as a token. Real tokens
  and session IDs almost always contain digits; strings with digits, consecutive capitals
  or all capitals are masked as before. The rule is identical to the hub and the other
  SDKs; the server agent uses the same `scrubber.text`.
- **Fingerprint side effect:** after upgrading, error messages containing such a name are
  grouped once under a new fingerprint; a new row appears in the dashboard and a one-time
  "new error" alert may fire.

## 0.2.1

### Fixed

- **The disk event repeated when the agent restarted.** The "once per mount point per
  hour" limit was kept only in memory, using a clock that reset with each process; an
  update, a server boot or `Restart=always` within the same hour re-sent the same
  `disk_full` event. Last-notified times are now stored in the state file
  (`disk_alerts`) using wall-clock time.

### Changed

- Tests run on Python 3.9–3.14 on every push (previously only on tags, on 3.12). The
  `requires-python >= 3.9` promise is now backed by tests. Publishing still happens only
  on `v*` tags.

## 0.2.0

### Added

- **Server agent: `vitalwatch-agent`.** Sends failures outside the application as error
  events to the hub's server endpoint: nginx/apache/Plesk vhost error logs
  (`web_server`, 502/504 inference, `route`), PHP-FPM (`php_fpm`), PostgreSQL,
  MySQL/MariaDB, MongoDB, Redis (`database`), failed units, OOM and kernel errors from
  journald (`service_failed`, `oom`, `kernel`), `systemctl --failed` every 5 minutes,
  `docker events` (`container_failed`: non-zero exit, ≥ 3 `die` within 10 minutes =
  restart loop, `unhealthy`, OOM), disk and inode usage (`disk_full`, once per mount
  point per hour) and user-defined `[log:<name>]` patterns (`log_error`). Commands:
  `run`, `check [--test]`, `systemd`. Standard library only; contract in
  `vitalwatch-doc` `features/22-sunucu-ajani`.
- The agent drops personal data before it leaves the server: IPv4/IPv6 → `[ip]`; nginx
  `client:`, `referrer` and `host` fields and Apache `[client …]` / `referer:` are
  removed entirely; query strings and fragments are stripped; then the package's existing
  masking is applied. SSH/authentication, access and mail logs are never read.
- Flow control: 20 events per minute for the same message, 300 per minute in total;
  bodies are split at 8 KB and at the 8 events per request the hub processes; if the hub
  is unreachable, up to 1000 events are buffered and retried with exponential backoff; a
  heartbeat every 5 minutes (`runtime: "agent"`). The hub's own domain is always ignored.
- Read positions (inode + offset) and the journald cursor live in
  `/var/lib/vitalwatch-agent/state.json`; log rotation and truncation are detected, a log
  seen for the first time is read from the end, and globs are rescanned every minute.

### Changed

- The `vitalwatch-status` update check now reads from PyPI (`info.version`); the hint is
  `pip install -U vitalwatch`. The README install line is `pip install vitalwatch`.
- `pyproject.toml`: SPDX license expression (`license = "MIT"`), `setuptools>=77` for
  builds. The old table format triggered a deprecation warning in setuptools.

## 0.1.1

### Added

- **Environment name normalization.** The hub only accepts production/staging/local and
  silently drops anything else — heartbeats included — with a 204. A project set up with
  `APP_ENV=development` or `prod` looked as if it sent nothing. Aliases are now mapped
  (`prod`/`live`, `stage`/`stg`/`preprod`/`uat`, `dev`/`development`/`test`/`testing`);
  an unknown value is sent as is and the diagnostic command reports an error. The table
  is the same across all three packages. Previously an unknown value was silently treated
  as `production`, mixing test data into live data.
- **Django middleware** (`vitalwatch.django.VitalWatchMiddleware`). Slow/5xx requests
  and uncaught exceptions; through the `got_request_exception` signal, errors from lower
  middleware also arrive with their stack trace. 4xx exceptions are not sent; the route
  pattern is sent. `VITALWATCH_HOOK_PROCESS = False` disables process hooks.
- **ASGI middleware** (`vitalwatch.asgi.VitalWatchASGIMiddleware`) — FastAPI, Starlette
  and other ASGI apps. Errors are reported and re-raised; if a class-bound
  `exception_handler` returns 5xx, the error still arrives with its stack trace. The
  route pattern is read from `scope["route"]` in FastAPI and from the router tree in
  Starlette.
- Same rules as Flask: one failure, one record; 4xx is not sent; the reporter is
  resolved at call time. Frameworks are imported only inside their own modules;
  dependencies stay at zero. Verified with Django 6.1, FastAPI 0.141 and Starlette 1.6.
- **The release tag is auto-detected** (`vitalwatch.release`). `VITALWATCH_RELEASE` was
  empty in almost every installation, so the hub could not tell which deploy an error
  started with. Order: `init(release=...)` → `VITALWATCH_RELEASE` (trimmed, ≤64) →
  `GIT_COMMIT`, `GIT_SHA`, `COMMIT_SHA`, `SOURCE_VERSION`, `VERCEL_GIT_COMMIT_SHA`,
  `RENDER_GIT_COMMIT`, `HEROKU_SLUG_COMMIT`, `CI_COMMIT_SHA` (first 12 digits, lowercase,
  if hex) → `.git` in the working directory (branch ref, `packed-refs`, detached HEAD,
  `gitdir:` file; only a valid 40-digit sha, first 12 digits; `ref:` only under `refs/`
  and without `..`). Git worktrees (`commondir`) are out of scope — use
  `VITALWATCH_RELEASE` there. With a `git pull` + gunicorn restart deploy, the new process
  reads the new commit itself. No subprocesses, never raises; the rule matches Node and
  Laravel. `vitalwatch-status` shows the tag and its source:
  `Release tag        abc123def456 (source: .git)`.
- **`vitalwatch-status` update check.** The package is not on PyPI; the newest stable
  version from the GitHub tags is shown (`Latest version`), and if it is
  newer than the installed version a warning line with a
  `pip install -U --force-reinstall` command is printed. It is a warning — the exit code
  does not change. On network/rate-limit errors it prints `could not check`;
  `VITALWATCH_STATUS_OFFLINE` (`1`/`true`/`yes`/`on`/`evet`) skips
  the check and the line entirely.
- **`memory_mb`**: slow request and `http_5xx` events carry the process's peak memory
  usage (RSS, MB) — the same field as Node and Laravel. Not sent on Windows, which lacks
  `resource`.

### Fixed

- **One failure produced two records.** Alongside the `exception` with a stack trace, a
  failing request also opened a stack-less `http_5xx` from `after_request`. The request is
  now flagged, and flagged requests do not open an `http_5xx`. The old test deliberately
  expected this double record and has been changed.
- **Errors were lost with `@errorhandler(Exception)`.** Flask treated the error as
  handled and teardown received `error=None`; only a stack-less `http_5xx` was sent. The
  app's `handle_user_exception` / `handle_exception` methods are now wrapped at instance
  level; if the handler returns 5xx the error is sent with its stack trace, if it returns
  4xx nothing is sent.
- **Hooks captured the reporter at setup time.** Calling `vitalwatch.init(...)` after
  `VitalWatchFlask(app)` sent events to the old instance. Request hooks,
  `sys.excepthook` / `threading.excepthook` / the shutdown flush and the heartbeat timer
  now all resolve the reporter at call time. If there was no configuration at setup time,
  the heartbeat never started; `init(...)` now retries it.
- **Process hooks were chained repeatedly.** Each `hook_process()` call wrapped the
  excepthook one more layer and added another flush to `atexit` (calling
  `VitalWatchFlask(app)` twice, every ASGI stack build). They are now installed once per
  process.
- **Calling `VitalWatchFlask(app)` twice produced double records.** `after_request` was
  registered twice, so every slow request and `abort(500)` produced two events; with
  `app.extensions["vitalwatch"]` the second setup is a no-op.
- **Setup could crash the application.** A non-UTF-8 `.env` (e.g. saved as cp1254) raised
  `UnicodeDecodeError` and broke `VitalWatchFlask(app)` and `vitalwatch.report()`.
  Unreadable files are skipped; `init_app` and `report()` never raise under any
  circumstances.
- **Flask: string status codes.** When a handler returned `("…", "500 ERROR")`, the 5xx
  was not recognized and the error became a stack-less `http_5xx`.
- **ASGI: class-bound handlers depended on middleware order.** If VitalWatch was not
  directly outside `ExceptionMiddleware` (e.g. GZip added after it, or
  `middleware=[VitalWatch, CORS]`), the handler's 5xx was sent without a stack trace.
  `ExceptionMiddleware` is now located along the `.app` chain on the first request.
- **ASGI: `BackgroundTasks` counted as slow requests.** Timing now stops once the last
  body chunk is sent; post-response work is not measured.
- **ASGI: nested middleware produced double records.** If a `Mount`ed sub-application
  also had the middleware, slow requests were sent twice; the request is now timed by the
  outer one.
- **The route pattern was computed on every request.** In Starlette, the router was
  scanned and patterns compiled for every fast 200 (~2 ms with 300 routes). The pattern is
  now computed only when an event will actually be sent, and Starlette candidates are
  cached. Flask and Django follow the same rule.
- **ASGI: the error check could replace the original error.** An exception whose
  `status_code` property raised would have had the new error take the original's place.
- **`VITALWATCH_TIMEOUT` units.** Node expects milliseconds under the same name; setting
  `2000` could make the process wait 2000 seconds for the hub. It is now seconds, with 100
  and above treated as milliseconds; invalid, zero/negative, NaN or infinite values fall
  back to 2 seconds, and the result is clamped to 0.1–10 seconds (a rule shared with the
  sibling packages).
- **Flask tests were not running.** In environments without Flask, five tests were
  silently skipped; the 0.1.1 changes were verified with Flask 3.0.0 (the version used by
  lens) installed.
- **Masking mangled readable names.** Upload file names now stay readable. Names of the
  form `<name>-<timestamp>-<random>.jpeg` showed up in the dashboard as
  `/uploads/discount/[token][card]-752066249.jpeg`: the timestamp was mistaken for a card
  number and the long name for a token.

  - **Card:** only sequences starting with 2–9 that pass Luhn are masked; millisecond
    timestamps start with 1. Known trade-off: a mistyped card number (which fails Luhn)
    and UATP cards starting with 1 are no longer masked.
  - **Token:** hex strings (UUIDs, hashes) containing an unbroken segment of 16+
    characters or containing letters are masked. Short segments joined by hyphens are
    readable names. Known trade-off: random keys split into short segments by separators
    (hyphens/underscores) — e.g. some base64url tokens with frequent hyphens/underscores —
    may pass through unmasked.
  - **Phone:** does not match when preceded by a digit. Timestamps whose last ten digits
    started with 5 used to become `179[phone]`.

  The rules are identical across the hub, `t.js`, Node, Laravel and Python; compared
  against 28 shared test vectors.

## 0.1.0

Initial release. Same scope as the sibling package `vitalwatch-node` 0.4.1.

- HMAC-signed server endpoint delivery (`/api/i/{key}/server`); redirects are not
  followed
- Personal data scrubbing (KVKK, Turkish data protection law): e-mail, phone, Turkish
  national ID (TCKN), IBAN, card numbers, tokens, SQL literals
- `exception` / `fatal` / `http_5xx` / `slow_request`
- Flask integration (`vitalwatch.flask.VitalWatchFlask`)
- Process hooks: `sys.excepthook`, `threading.excepthook`
- 8-hour heartbeat
- `vitalwatch-status` diagnostic command (`--test`, `--vitalwatch`)

Differences from the Node package and why:

- **Send queue.** In Node, `fetch` is already an un-awaited promise; since WSGI is
  synchronous, events here are placed in a bounded queue and sent by a single background
  thread. When the queue is full, events are dropped — blocking would slow down the
  monitored application.
- **Deduplication.** Node uses a `WeakSet`; in Python, built-in exceptions do not accept
  weakrefs (`weakref.ref(ValueError())` → `TypeError`), so the marker is carried on the
  exception itself.
- **Fork cleanup.** Gunicorn forks with `--preload`; `os.register_at_fork` rebuilds the
  queue in the child process — otherwise events would be written to a dead thread.
- **Unicode patterns.** Python `re` does not support `\p{L}`; equivalents are built with
  `\w` / `[^\W\d_]`, and behavior on realistic input is the same.
